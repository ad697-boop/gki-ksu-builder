# 踩坑记录（已全部修复）

按时间顺序，包含对应 git commit（前 7 位）。

## 1. GKI 方案全灭（方向性）

早期 builder 用 GKI android12-5.10 + KernelSU 编出 `Image-ksu-5.10.245`，刷入无限重启。结论：cupid 内核不是 GKI，必须用高通 OSS 内核源码。见 `docs/00-背景与根因.md`。

## 2. payload-dumper CLI 不兼容

- xishang0128 版 v0.1.6：`unknown command "boot"`（CLI 改了）。
- 修复：换 ssut/payload-dumper-go v2.0.2。
- 又踩：ssut 的 release tag 是 `2.0.2` 没有 `v` 前缀，URL 写 `v2.0.2` 会 404（commit `2e2e6f2`）。
- tar 里二进制名是 `payload-dumper-linux-amd64-v3`，不是 `payload-dumper-go`，要用 find 动态找（commit `a29eed6` 附近）。

## 3. magiskboot 日志走 stderr

`magiskboot unpack | tee unpack.log` 收不到输出（日志在 stderr），`grep HEADER_VER` 失败。修复：`2>&1 | tee`（commit `474f40a`）。

## 4. magiskboot 选型

- jiamils KernelSU_Action 的 Rust 版 magiskboot：repack 报 `No such file or directory (os error 2)`。
- 修复：换官方 Magisk APK 里的 `lib/x86_64/libmagiskboot.so`（静态 ELF，sha256 固定）（commit `71b9ece`）。
- 又踩：官方 APK 里的是 **Android 版**，跑不了 Linux？——不对，magiskboot 是静态链接，能跑。真正问题见下条。

## 5. repack 找不到 boot.img

`magiskboot repack boot.img` 报 ENOENT——因为解包时只读了 `../rom_out/boot.img`，没把它复制进工作目录。修复：解包后 `cp ../rom_out/boot.img boot.img`（commit `a4403ab`）。

## 6. runner OOM（exit 143）

full LTO 在 2 核/7GB runner 上被杀（143=SIGTERM）。修复：
- full LTO → thin LTO（不影响 vermagic/模块兼容）（commit `f9b4c7a` 前身）
- 加 8G swap；runner 自带 /swapfile，需先 `swapoff -a` 再重建（commit `8ad839f`）。

## 7. SukiSU builtin 分支 5.10 编译 bug（已由上游修复）

`sulog/event.c` 的 `USER_ARG_NULL` 宏返回指针但参数要结构体。早期加了 sed 补丁 `(*user_arg_null_ptr())`；后来上游把参数改成指针，旧补丁反而改坏（报 `take the address with &`）。修复：删除过期 sed（commit `f9b7ad1`）。

## 8. SukiSU 分支与驱动版本

- builtin 分支（SUSFS 版）最初在 5.10 编译失败（见上条）。
- `KSU_VERSION` 不是由 tag 决定，而是 `40000 + main 分支提交数 - 2815`（实时查 GitHub API）。只 pin tag 没用。
- 修复：输入 `ksu_version`，用 sed 把 Kbuild/Makefile 里的 `KSU_VERSION :=` 强制写死（commit `0741423`）。

## 9. vermagic 多一个 `+`（最重要）

`CONFIG_LOCALVERSION_AUTO=n` 且内核在 git 仓库里、又没设 LOCALVERSION 环境变量时，setlocalversion 的 `--short` 分支输出 `+`（脏树标记），vermagic 变成 `5.10.256-gki-ge682ed2de56f+`，与原厂 vendor 模块（无 `+`）不匹配 → 模块全拒载。

- CI 版本校验最初是**前缀匹配**，没拦住。
- 修复：构建时 `export LOCALVERSION=""` 抑制 `+`；校验改为 vermagic **精确相等**（commit `e4db466`）。

## 10. 副产物：CONFIG_MODULE_SCMVERSION 丢失

`MODULE_SCMVERSION` 依赖 `LOCALVERSION_AUTO`，关掉 AUTO 后 olddefconfig 会丢弃它。纯调试属性，不影响模块加载，接受。

## 11. ReKernel-X LKM 编译

- 官方模块 zip 的 .ko 是给别的内核编的（vermagic `5.10.252-dirty`），本机 insmod 静默失败 → "刷入不生效"。
- 修复：用同内核 Module.symvers 重新编译（commit `294e00a` 起）。
- `#include "../android/binder_internal.h"` 是相对路径 → 源码必须放内核树 `drivers/rekernel_x` 下（commit `fd38b13`）。
- `No rule to make target 'scripts/module.lds'`：`make Image` 不生成 module.lds，需先 `make modules_prepare`（commit `63dd62b`）。
- `Symbol version dump Module.symvers is missing`：`make Image` 只生成 `vmlinux.symvers`，外部模块 modpost 读 `Module.symvers`，需手动 `cp vmlinux.symvers Module.symvers`（commit `63dd62b`）。
- 符号依赖核查：`kallsyms_lookup_name` 不需要导出（模块用 kprobe 拿地址）；`android_vh_binder_alloc_new_buf_locked` 在本内核已 `EXPORT_TRACEPOINT_SYMBOL_GPL`。

## 12. SUSFS

- SukiSU 的 SUSFS 驱动代码在 **builtin 分支**（Kconfig 带完整 SUSFS 菜单），main 分支没有。
- 内核侧补丁来自 susfs4ksu `gki-android12-5.10` 分支（`50_add_susfs_in_gki-android12-5.10.patch` + `kernel_patches/fs/*` + `kernel_patches/include/linux/*`）。
- 不要打 `kernel_patches/KernelSU/10_enable_susfs_for_ksu.patch`——那是给原版 KernelSU 的，builtin 已自带。
- 补丁在 LineageOS 树上的冲突风险：若 `patch -p1` 失败，日志在 `susfs_patch.log`。
- 管理器"Seccomp status"显示"未启用"是正常的：seccomp 集成只有 main 分支有，builtin（SUSFS）没有，不影响 root/隐藏。

## 13. SUSFS 内核下"应用拿不到 root / app profile 更新失败"（协议版本不匹配）

现象：SUSFS（builtin 最新代码）刷入后，管理器能识别驱动（显示"工作中"），但：

- 更新 app profile 报 `Unsupported profile version: 3` / `Failed to set app profile: invalid profile!`
- 应用无法获得 root

根因：**builtin 分支最新代码比 v4.1.3 管理器新太多**。内置驱动只是被强制把版本号显示成 40796，实际协议（app profile ABI）已经升级：

- v4.1.3 管理器（2026-06-02 发布）发 **profile 版本 3**
- builtin HEAD（如 5a2bb7e5，2026-08-14）只认 **profile 版本 4**（`KSU_APP_PROFILE_VER=4`）

修复：SUSFS 构建时把 builtin **pin 到 v4.1.3 同期的提交 `6c13a069`**（2026-05-30，`KSU_APP_PROFILE_VER=3`），
workflow 新增 `ksu_commit` 输入（默认 `6c13a0695a1115e1000c998872b66f4ff5b2f11e`）。
验证过：6c13a069 在 `CONFIG_KSU_SUSFS=y` 下 sulog 能正常编译（capture 参数是指针版，与宏匹配，不需要 sed 补丁）。

另外注意：builtin 提交 `b8279c30`（2026-06-09 "implement uapi version"）是协议变更点，**不要 pin 到它或之后**。

## 14. /system/bin/su 缺失（内置内核的 su 来源）

现象：内置内核（无论 main 还是 builtin）刷入后，`/system/bin/su` 不存在，传统 su 应用拿不到 root。

排查结论：

- 内核驱动只**钩住** `/system/bin/su` 的 exec（sucompat），不负责创建 su 文件；
- `ksud install`（管理器"直接安装"）只把 ksud 放到 `/data/adb/ksud`，**不创建 /system/bin/su**；
- ksud 开机确实运行（内核日志 `escape to root for init executing ksud`、`post-fs-data triggered`），允许列表、模块挂载都正常，唯独 su 文件缺失。

临时修复（模块法）：做一个 KSU 模块，把管理器 APK 里的 `lib/arm64-v8a/libksud.so` 作为
`system/bin/su`（0755）放进模块 → 管理器安装 → 重启后 overlay 提供 `/system/bin/su`，
应用执行 su 时内核按允许列表授权，su（ksud 本体）拉起 root shell。模块包：`D:\codex\ksu_su_provider.zip`。

注意：用 pin 到 6c13a069 的内核后，是否还需要这个模块取决于实际测试（与 v4.1.3 时代 main 构建行为应一致）。
